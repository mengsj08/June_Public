Why this skill

它解决的不是“生成一段日报”，而是把日报变成可交接的团队执行流程。

这个 skill 适合放在团队成员自己的电脑上运行。账号、仓库、飞书机器人都归这台电脑所有；Codex 或其他人只需要按流程指导，不需要接触凭据。

每天变化分散在多个系统

GitHub 提交、任务卡状态、Feishu/Wiki 文档更新分散存在，靠人工回忆很难写清“谁做了什么”。

同步和发送要分开

先本地拉取和生成审阅稿，确认无误后才允许测试发送，避免把调试报告直接发到正式群。

消息格式需要团队自己调

原始报告偏机械，最终飞书消息应由团队按真实阅读习惯调整 prompt，再固定为自动化任务。

What it installs

一套本地控制层，不绑定作者电脑，不复制凭据。

初始化后，所有运行材料都在目标电脑的 `~/Documents/TeamSpace` 下。仓库名、仓库地址、Feishu/Wiki 导出命令、飞书机器人都由使用者在本机配置。

1

控制脚本

`team_sync_reporter.py` 负责 init、doctor、run、send 和生成 WorkBuddy prompt。

2

本地配置

`team-sync-reporter.config.json` 记录仓库、同步命令、报告窗口和发送模式。

3

消息 prompt

`feishu-message-prompt.md` 专门控制最终发到飞书群的文案结构和口吻。

4

WorkBuddy 定时任务

测试发送成功后，把生成的 prompt 或 daily shell 脚本交给 WorkBuddy 每天执行。

Launch sequence

从空机器到每日自动发送，需要先跑完七个关口。

每一步都有明确产物。只要 doctor、run、消息格式、测试发送没有闭环，就不应该启用正式自动发送。

01

用户指定仓库名和 GitHub 地址

初始化时必须显式传入 `--repo-name` 和 `--repo-url`，skill 不猜组织名，也不默认某个团队仓库。

user input
02

本机填写密钥和飞书机器人

凭据只放在本地 env 文件或系统环境变量里。文档、聊天、报告、仓库都不承载真实值。

local secret
03

运行 doctor 做前置检查

检查 Python、GitHub 登录、仓库配置、Feishu/Wiki 同步命令、发送目标变量是否齐全。

preflight
04

先 run，不发送

同步 GitHub 与 Feishu/Wiki，写入本地 raw、state、review-queue，生成可审阅的机械报告。

no send
05

根据测试报告调整飞书消息 prompt

让团队自己定义标题、分组、语气、谁做了什么、无 Feishu 变更时怎么写。

message polish
06

发送测试飞书消息

只发到测试机器人或测试群，确认格式、目标和敏感信息边界都正确。

test target
07

启用 WorkBuddy 每日任务

最后再把生成的 WorkBuddy prompt 或 daily shell 脚本设为定时自动化。

daily automation

Configuration boundary

仓库和密钥都由使用者本机配置，页面和 skill 只提供模板。

这个边界是为了让 skill 可以交给不同团队成员使用，同时避免把作者机器上的路径、组织信息或凭据带过去。

需要用户明确填写

这些值代表当前团队和当前电脑，不能由 skill 作者预设。

  • `github.repos[].name`：本地目录名。
  • `github.repos[].url`：GitHub HTTPS 或 SSH 地址。
  • `feishu.sync_commands`：实际可用的 Feishu/Wiki 导出命令。
  • `send`：测试和正式飞书机器人的环境变量名。

永远不写进页面或仓库

这些材料只属于执行电脑本地，页面只提示路径，不展示值。

  • Webhook、sign secret、app secret、cookie、token。
  • 邮箱密码、chat id、私有飞书文档 token。
  • WorkBuddy trace、调试日志里的敏感参数。
  • 任何真实 `.env` 内容或终端截图中的凭据。

Message loop

日报先生成“证据稿”，飞书消息再由 prompt 调到团队能读的样子。

推荐的调试节奏

不要急着启用发送。先让使用者看到原始报告的生硬程度，再决定群消息要怎样表达。

  1. 运行 `run` 生成 review-queue 草稿。
  2. 阅读 JSON evidence 和 Markdown 报告。
  3. 修改 `feishu-message-prompt.md`。
  4. 重新生成最终飞书消息。
  5. 满意后 `send --target test`。
  6. 测试群确认后，才设置每日自动化。

feishu-message-prompt.md 应该固定这些口径

标题 团队工作更新摘要（YYYY-MM-DD）
总体 GitHub 提交数、Feishu/Wiki 源文档变更数、今日主线。
人员 按负责人分组，写任务编号、任务名、状态、实际推进动作。
飞书 有变更列文档；无变更明确写“本时间窗口内未检测到 Feishu/Wiki 源文档新增或修改”。
下一步 最多 3-5 条，只保留需要团队确认或继续推进的事项。

初始化 TeamSpace 
python3 /path/to/workbuddy-team-sync-reporter/scripts/team_sync_reporter.py init \
  --root "$HOME/Documents/TeamSpace" \
  --repo-name "<local-repo-name>" \
  --repo-url "https://github.com/<org>/<repo>.git"
创建本机密钥文件 
mkdir -p ~/.config/team-sync-reporter
cp ~/.config/team-sync-reporter/secrets.example.env ~/.config/team-sync-reporter/secrets.env
chmod 600 ~/.config/team-sync-reporter/secrets.env
预检与本地生成 
python3 ~/Documents/TeamSpace/automation-control-plane/team_sync_reporter.py doctor \
  --config ~/Documents/TeamSpace/config/team-sync-reporter.config.json

python3 ~/Documents/TeamSpace/automation-control-plane/team_sync_reporter.py run \
  --config ~/Documents/TeamSpace/config/team-sync-reporter.config.json
测试发送与 WorkBuddy 
python3 ~/Documents/TeamSpace/automation-control-plane/team_sync_reporter.py send \
  --config ~/Documents/TeamSpace/config/team-sync-reporter.config.json \
  --target test \
  --message-file <final-feishu-message.md>

python3 ~/Documents/TeamSpace/automation-control-plane/team_sync_reporter.py workbuddy-prompt \
  --config ~/Documents/TeamSpace/config/team-sync-reporter.config.json
