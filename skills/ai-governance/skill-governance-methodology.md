# 把 Skill 从“文件堆”变成可控系统

## 先讲一个大概率发生在你身上的故事

你同时用着三个 AI 编码工具——比如 Claude Code、Codex，再加一个 Cursor。过去半年里，你自己装过一些 skill 和插件，AI 也“顺手帮你装了几个”，项目模板又自带了一批。某天你想找上个月用过的那个特别顺手的重构 skill，然后发现：

- 你不记得它装在哪个工具里，甚至不确定它叫什么名字；
- 你在其中一个工具里翻到一个同名目录，但不知道它现在还能不能用——文件在，不代表工具认它；
- 你让 AI“帮我清理一下没用的 skill”，它爽快地回答“已清理完成”，但你完全不敢信：它到底删了什么？依据是什么？万一删掉的正是你下周要用的那个呢？

这不是整洁强迫症的问题。我们认为这件事值得认真管，理由有三个：

1. **AI 会替你装东西**。资产的增长速度已经超过人脑记账的速度——你不再是唯一往系统里加东西的人。
2. **“文件在”不等于“能用”**。每个工具有自己的发现机制、启用开关和作用域规则，一份文件躺在磁盘上，和它出现在工具的菜单里，是两回事。
3. **想让 AI 管 AI，前提是每一步有证据**。没有证据的自动清理、自动启停、自动汇报，不是省心，是把混乱自动化了。

下面是我们沉淀出的一套方法，外加一个可以直接拿去用的工具。

## 先问四个问题

当 Skill 从十几个涨到几百个，真正难的不是再做一个 Skill，而是对任何一个 Skill 都能回答四个问题：**我是否长期拥有它？它在哪些工具里有副本？现在是否真的可用？最近是否在真实任务中成功过？**

这四个问题不能靠“扫描到目录”代答。创作不等于使用；`adopted` 只表示长期保留一个规范源，不等于常驻菜单；登记和测试收尾不等于业务真实使用；市场缓存、镜像和候选包更不该自动变成人的治理积压。

## 先分开三种权威

> 说人话：这就像一套房子的三份文件——房产证证明这房子归你，水电表反映此刻的实际用量，装修验收单证明某次施工确实合格。三份文件谁也不能替谁说话：水电表走字不能证明房子是你的，房产证也不能证明上周的装修没偷工减料。这一节解决的麻烦是：**AI 说“我看到它开着”，你说“我记得我关了它”，到底听谁的——答案是各记各的账，不一致本身就是重要信息。**

治理系统至少有三类事实源，互不冒充：

1. **人的决策是意图正本**：要不要长期采纳、默认暴露、退役或发布。
2. **工具配置是运行事实**：某个工具此刻发现了什么、启用了什么、作用域是什么。
3. **测试记录是执行证据**：某次操作是否执行、完成并通过验证。

例如，决策账本写“默认关闭”，工具配置却显示“开启”，结论应是“意图与运行状态不一致”，而不是悄悄改写任一方。测试通过也只能证明测试时刻的行为，不能反推当前意图。

```yaml
decision:
  asset_id: lint-helper
  desired_exposure: on_demand
  decided_at: 2026-03-01T10:00:00Z
runtime_observation:
  ecosystem: tool-a
  actual_state: enabled
  observed_at: 2026-03-02T08:30:00Z
execution_evidence:
  operation: reconcile_exposure
  result: not_started
```

## 资产身份与运行副本分开

> 说人话：一首歌是一个作品，但它可以同时上架在好几个音乐平台——每个平台有自己的编号、上架状态和地区限制，某个平台下架了不等于这首歌消失了。Skill 也一样：它本身是一个资产，装在每个工具里的只是一份“上架副本”。这一节解决的麻烦是：**同一个 skill 在三个工具里有三份副本、三种状态，如果不把“它是什么”和“它装在哪”分开记，你永远说不清自己到底有几个 skill。**

一个逻辑 Skill 只建一条 `SkillAsset`。它描述规范源、来源、成熟度和用途。每个工具里的安装、插件子项、项目副本或市场包分别建一条 `DeploymentRecord`。

```yaml
skill_asset:
  id: lint-helper
  canonical_ref: skills/lint-helper
  maturity: adopted
deployments:
  - ecosystem: tool-a
    native_id: lint-helper
    scope: user
    desired_exposure: on_demand
    actual_state: enabled
  - ecosystem: tool-b
    native_id: lint-helper@example-market
    scope: project
    desired_exposure: hidden
    actual_state: disabled
```

`desired_exposure` 属于治理意图，`actual_state` 属于原生工具观测。两者可以暂时不同。市场缓存只是一个部署或缓存事实，不会因此升级为规范源，也不会自动生成“请处理”卡片。

## Capability 必须带证据

> 说人话：一份靠谱的体检报告只写查过的项——查了血压就写血压数值，没查骨密度就写“未检”，绝不会把“没查”写成“大概正常”。工具能力也该这样报告。这一节解决的麻烦是：**AI 很容易把“我应该能关掉它”说成“我能关掉它”，等你真让它关的时候才发现根本没这条路，或者更糟——它用了一条没人验证过的野路子。**

Adapter 的每项能力使用固定等级：

| 等级 | 含义 |
| --- | --- |
| `native` | 由原生 API、CLI 或事件接口直接提供 |
| `verified_fallback` | 非原生路径，但已用隔离测试验证并具备回滚方式 |
| `read_only` | 只能可靠观测，不能修改 |
| `unsupported` | 生态明确不提供，或治理边界禁止 |
| `unknown` | 尚未核验，不能猜测 |

每个结论必须附核验时间和证据指针：

```yaml
set_enabled:
  level: native
  verified_at: 2026-03-02T09:00:00Z
  evidence_ref: receipts/tool-a-toggle-smoke.json
install:
  level: unknown
  verified_at: null
  evidence_ref: notes/install-not-tested.md
```

`unknown` 不能在界面或自动化里降级成“大概支持”。最实用的核验手段是隔离 home 冒烟：创建临时目录，通过工具支持的 home 环境变量（例如 `CODEX_HOME` 或 `CLAUDE_CONFIG_DIR`）启动真实 CLI，放入虚构 Skill，执行“发现 → 修改 → 重读 → 回滚”，最后删除临时目录。测试不得读取或复制真实 home，也不得触碰凭据。

```python
with TemporaryDirectory() as temp:
    env = {**os.environ, "TOOL_CONFIG_DIR": temp}
    run(["tool", "plugin", "list"], env=env, check=True)
```

## 决策台只呈现人的判断

> 说人话：一个好助理不会每十分钟来汇报一次“文件已归档”，而是只在需要你签字的时候才出现，并且把“签什么、为什么、签错了会怎样”一次说清。这一节解决的麻烦是：**如果治理系统把几百条扫描结果都摆到你面前，你要么全部忽略，要么被拖进无穷的“处理积压”——两种结局都等于没有治理。**

首页不是资产总表，也不是扫描告警墙，只放必须由人裁决的事项。每张卡至少写清：AI 推荐、推荐依据、选错的代价、批准后的动作范围和独立红线。

可恢复且低风险的动作，一次批准后应执行完整闭环。暂缓事项按条件唤醒，例如“下一次真实任务需要此能力时”或“上游发布兼容版本时”，不要每隔七天骚扰一次。相同、可恢复、非红线的决定连续出现 2–3 次，可以提议压缩成默认委托，并保留撤销入口。

发布、删除、付费、凭据读取或传递始终独立确认。它们不会因为已有默认委托而被吞并。

## 使用证据不能一步跳到成功

> 说人话：说自己“坚持健身”，聊天记录里的“我要去健身房了”不算数，打卡照片和训练记录才算数。Skill 的“好用”也一样，需要分层的证据，而不是一句自我评价。这一节解决的麻烦是：**AI 汇报“任务完成”时，你无法区分它是真跑完并验证过，还是只是跑了个开头、甚至只是打算跑。**

真实使用至少分四层：

- `selected`：调度器或人选择了 Skill。
- `executed`：Skill 的脚本、提示或工具实际运行。
- `completed`：运行到声明的结束状态。
- `validated`：满足预先定义的验证契约。

扫描到文件最多证明“存在”；日志显示调用最多证明 `executed`。只有先定义验证契约，例如“输出 JSON 通过 schema 且目标测试全绿”，才能记录 `validated`。没有契约就不能让 Skill 自证成功。

```yaml
usage_event:
  asset_id: lint-helper
  stage: completed
  validation_contract: null
  validated: false
  note: execution finished, outcome not independently verified
```

## 现成的工具：skill-ecosystem-adapters

上面这套方法不必从零实现。我们把它做成了一个包：`skill-ecosystem-adapters`——纯标准库的 Python 包，零外部依赖。它是“一物两态”：既可以当普通 Python 库在脚本里调用，也可以当作一个 skill 装进 AI 工具，让 AI 按其中写好的安全剧本替你操作。每项能力都按上一节的等级表标注、附带核验证据，但不同生态的支持深度并不相同。

| 生态 | 真实支持范围 |
| --- | --- |
| Codex / Claude | 原生发现、读取与启停；写操作仍按“先读 → 写入 → 回读核验”执行 |
| WorkBuddy / BigApple | 我们环境中的参考实现，读者应把目录和 CLI 约定当模板核对，而不是通用保证 |
| Cursor / Windsurf / 自研工具等 | 使用 `GenericAdapter` 扫描显式配置的目录，可做盘点和路径排障；只报告存在性与 scope，不支持启停 |

它能帮你做什么，按场景说：

- **跨工具盘点**：一条命令跑遍所有 adapter 的 `discover()` 和 `read_state()`，输出一张“生态 × skill × 启用状态”的资产表。某个工具当时不可用，就如实标 unavailable，不猜绿色状态。
- **“为什么这个 skill 没触发？”排障**：先查它在那个工具里到底有没有被发现、启用了没有、作用域是用户级还是项目级——大多数“skill 失灵”其实是这三样之一没对上。
- **清理斜杠菜单**：安全地关掉不用的入口。写操作严格按“先读 → 写入 → 回读核验”执行并保存 receipt，目前仅在 Codex 和 Claude 上开放（这两条路径是 `native` 级），其他生态的写能力未验证就是不能用。
- **换新电脑**：迁移前用 `export_observations(adapters)` 保存 JSON 清单，迁移后再次导出，再用 `diff_observations(old, new)` 得到新增、消失、状态变化三组；结果用于对账，不会自动安装或删除。
- **定期漂移检查**：把 `{"生态/id": "default|on-demand|disabled"}` 意图 JSON 与 `export_observations(adapters)` 的结果传给 `drift(intent, observations)`；不一致才列出，观测不到的项明确标成 `missing`。
- **接入其他工具**：给 `GenericAdapter("cursor", roots)` 传入已确认的 skill 根目录，即可让开篇故事里的 Cursor 参与盘点；这条通用路径不声称能读取或修改 Cursor 的原生启停状态。
- **隔离测试法**：自带冒烟脚本，在临时目录里建一个假 home、放虚构 skill、走完“发现 → 修改 → 重读 → 回滚”，全程不碰你的真实环境。就算你不用这个包，这也是一份“怎么安全测试 AI 工具配置”的教材。
- **边界**：发布类动作永远由人来点，这个包永不代做；未验证的能力（`unknown` / `unsupported`）在能力表里明说不能用；永不读取、复制或展示凭据。

## 不止 Skill：所有“AI 替你攒下的资产”都适用

把镜头拉远一点：prompt 库、自动化脚本、定时任务、工具配置、MCP 连接——凡是 AI 参与积累、多处有副本、状态会漂移的资产，都适用同一套骨架：**意图、运行状态、执行证据分开记账；资产身份和部署副本分开建档；能力必须带证据分级；人只裁决必须由人裁决的事；“成功”必须有独立验证。**

最终目标不是让资产覆盖率看起来更高，而是让每个需要人的决定更少、更准，让批准后的运行事实可复核，让“成功使用”始终有独立证据。方法在文中，工具在包里，拿去用。
